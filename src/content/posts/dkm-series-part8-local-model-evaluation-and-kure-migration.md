1\~7편에서는 문서 전처리, 하이브리드 검색, 질의 해석, CSV 계산과 답변 인용 검증까지 RAG 파이프라인의 핵심 기능을 완성했다. 기능을 모두 갖춘 뒤 마지막으로 풀어야 할 과제는 운영 비용과 실행 환경이다.

문서 등록 시와 질문마다 외부 임베딩 API를 반복 호출하면 지속 비용이 커지고 사내 문서가 외부로 전달된다. 그렇다고 검증 없이 로컬 모델로 바꾸면 기존 DB와 충돌하거나 답변 품질 회귀가 발생한다. 마지막 8편에서는 로컬 `KURE-v3` 전환 시 기존 스키마를 지키는 0 패딩 원리와 경량 리랭커 교체 보류 판단 두 가지를 살펴본다.

---

## 1. 0 패딩과 KURE-v3 검증

DKM은 초기에 OpenAI 임베딩 모델(`text-embedding-3-large`)을 기본 `1,536`차원 설정으로 도입했다. 이 때문에 PostgreSQL의 `pgvector` 벡터 저장 컬럼도 당시 모델 출력 길이에 맞춰 `1,536`차원으로 만들어져 있었다. (`pgvector` 자체가 1,536차원을 강제하는 것은 아니지만, 이미 OpenAI 벡터가 쌓인 컬럼 크기를 바꾸면 기존 데이터와 공존할 수 없다.) 이후 로컬 한국어 모델 `KURE-v3`(`1,024`차원)로 전환하려 하자, `1,024`차원 출력을 기존 `1,536`차원 컬럼에 맞추는 문제가 생겼다.

`storage_vector()`는 `1,024`차원 출력을 기존 `1,536`차원 컬럼 규격에 맞게 변환한다. 먼저 입력이 길이 `1,024`의 숫자 리스트(`bool` 제외)인지 확인한다. 이어서 벡터 길이를 `1`로 맞추는 L2 정규화를 수행하고, `NaN`, 무한대, 크기가 0인 영벡터는 `502` 오류로 막는다. 검색 시 코사인 유사도는 벡터 크기가 아니라 방향 각도만 비교한다. 저장 시 모든 벡터 길이를 `1`로 맞춰 두면(기존 OpenAI 벡터도 동일), 조회할 때 길이를 나누지 않고 내적만으로 같은 순위를 계산할 수 있다.

마지막으로 `storage_vector()`는 정규화된 `1,024`차원 벡터 뒤에 `0.0`을 `512`개 붙여 `1,536`차원으로 반환한다. 같은 위치의 숫자끼리 곱해 모두 더하는 내적 계산에서는, 뒤 `512`칸이 모두 `0`이면 `0 × 0 = 0`만 더해진다. 각 벡터의 길이를 계산할 때도 `0`의 제곱은 `0`이므로 길이가 `1`인 상태가 그대로 유지된다. 예를 들어 `2`차원 벡터 `(0.6, 0.8)`과 `(1.0, 0.0)`을 곱해 더하면 `0.6 × 1.0 + 0.8 × 0.0 = 0.6`이다. 뒤에 `0`을 붙여 `(0.6, 0.8, 0)`과 `(1.0, 0.0, 0)`을 내적해도 `0.6 × 1.0 + 0.8 × 0.0 + 0 × 0 = 0.6`으로 같다.

```python
# backend/knowledge/integrations/kure.py — 1,536차원 저장소 호환을 위한 0 패딩 변환
# - vector:           로컬 KURE 워커가 반환한 1,024차원 실수 리스트
# - normalize_prefix: 앞 1,024차원의 유한성과 영벡터 여부를 검증하고 L2 정규화를 수행하는 내부 도우미
# - AppError:         상태 코드와 오류 식별자를 담아 API와 워커 공통 오류 응답을 만드는 예외 래퍼

def storage_vector(vector):
    # 파이썬에서 bool은 int의 하위 클래스이므로 isinstance 대신 type(v)로 엄격히 걸러낸다.
    if not isinstance(vector, list) or len(vector) != 1024 or any(type(v) not in (int, float) for v in vector):
        raise AppError(502, 'invalid_embedding', 'KURE 벡터의 차원이나 값이 올바르지 않습니다.')
    return normalize_prefix(vector, 1024) + [0.0] * 512
```

교체 전후 공정한 비교를 위해 키워드 검색, 순위 융합, `BGE v2-m3` 리랭커를 모두 고정했다. `24,000자` 근거 예산과 1차 후보 상한(`60`개), 재순위 상한(`200`개)도 유지한 채 **벡터 유사도 순위만** `KURE-v3`로 바꿨다.

| 평가 집합 (필수 원문 수) | OpenAI (기존) | KURE-v3 (후보) | 관찰 결과 |
| --- | ---: | ---: | --- |
| 실자료 한국어 30문항 (`56`곳) | 최종 입력 `45/56` | **최종 입력 `46/56`** | 벡터와 BGE 전달 `55 -> 56` 증가로 장비 제어 설명 1곳 확보 |
| 별도 한국어 회귀 28문항 (`58`곳) | 최종 입력 `58/58` | 최종 입력 `58/58` | 회귀 손실 `0`건 유지 |
| 일본어 5문항 (`7`곳) | 입력 `7/7`, 인용 `7/7` | 입력 `7/7`, 인용 `7/7` | 복제 DB 일본어 PDF 매뉴얼 동등 유지 |
| 중국어 5문항 (`5`곳) | 입력 `5/5`, 인용 `4/5` | 입력 `4/5`, 인용 `4/5` | 간체 HSMS 타이머 표 1곳 예산 이탈, 영어 문서 인용 유지 |

중국어 5문항에서 `5/5`가 `4/5`로 줄어든 수치는 **최종 입력 기준**이다. 간체 중국어 장비 통신(HSMS) 문서의 타이머 표는 양쪽 모두 BGE 점수가 `-4.9765625`로 같았다. 그러나 KURE 쪽에서 `-4.9765625`보다 점수가 높은 경쟁 후보가 늘며 순위가 12위에서 29위로 밀렸고 24,000자 예산 밖으로 빠졌다. 다만 같은 `T3 45초`, `T6 5초` 값을 담은 영어 설계 문서가 양쪽 모두에 전달됐다. OpenAI와 KURE 모두 답변에서는 중국어 표 대신 영어 문서를 인용해 실제 인용 수치는 `4/5`로 같았다.

## 2. 리랭커 교체 보류와 판단 근거

임베딩을 `KURE-v3`로 전환한 뒤, GPU 메모리(VRAM) 부담을 더 줄이려는 실험이 이어졌다. 당시 `BGE v2-m3` 리랭커가 GPU 메모리 `1,154 MiB`를 점유해 4GB GPU에 `KURE-v3`까지 함께 올리기 어려웠다. 그래서 리랭커를 더 가벼운 `KURE-Reranker-nano`(`537 MiB`)로 교체할 수 있는지 검증했다.

공정 비교를 위해 이미 계산한 `KURE-v3` 벡터 순위와 키워드, 융합 후보, 질의 전처리 스냅샷을 동일 해시로 고정하고 `BGE`와 `nano`만 교체했다. 재정렬 시간은 `RTX 3050 Laptop 4GB`(GPU `FP16`, 한도 `4,096`토큰, 배치 `1`, 잘림 `0`건)에서 측정했다. 모델 예열 후 점수 캐시를 끄고 70\~193쌍 규모의 질의 18건 소요 시간을 쟀다.

| 평가 항목 | BGE v2-m3 (유지) | KURE-Reranker-nano (보류) | 판정 근거 |
| --- | ---: | ---: | --- |
| 실자료 한국어 30문항 (`56`곳) | 최종 입력 `46/56` | 최종 입력 `47/56` | `+4`곳 확보, `-3`곳 손실 |
| 별도 한국어 회귀 28문항 (`58`곳) | 최종 입력 `58/58` | 최종 입력 `54/58` | 센서와 보드 핵심 절차 4곳 손실 |
| 영어 6문항, 중국어 5문항 | EN `7/10`, ZH 입력 `4/5` | EN `9/10`, ZH 입력 `5/5` | ZH 실제 답변 인용은 양쪽 `4/5` 동일 |
| 재정렬 지연 (중앙값, p95) | `4.04초`, `4.58초` | `4.27초`, `5.13초` | 중앙값 `+6%`, p95(95% 완료 기준) `+12%` 증가 |
| 최대 GPU 메모리 할당 | `1,154 MiB` | `537 MiB` | 메모리는 절반 절감 (`-53%`) |

결과는 **교체 보류(`BGE v2-m3` 유지)**였다. GPU 메모리를 절반(`537 MiB`)으로 줄였고 한국어 30문항 확보 수도 1곳 늘었다. 하지만 기존에 다 찾던 회귀 집합은 `58/58`에서 `54/58`로 떨어졌다. 배치 크기 1 기준 재정렬 속도도 오히려 느려졌다(`4.04초 -> 4.27초`). 중국어 타이머 표 역시 리랭커 순위가 29위에서 6위로 올라 최종 입력에는 들어왔지만, 실제 답변 인용(`4/5`)은 늘지 않았다.

실자료 한국어 손실 3곳과 회귀 손실 4곳을 합친 7개 구간은 모두 첫 재정렬 후보 풀 안에 있었다. 다만 탈락 원인은 두 가지였다. 장비 제어 원문은 `nano`가 실제로 순위를 `14위 -> 42위`로 낮춘 사례였다. 반면 공정 수치 후속 질문의 두 구간은 `nano`가 BGE보다 순위를 높여 주었다. 그런데도 달라진 상위 후보 조합 때문에 뒤쪽 보충 선택 단계가 다른 긴 구간을 먼저 채우면서 `24,000자` 예산 밖으로 밀려났다.

후속 문맥 선택 파이프라인을 함께 수정하면 탈락한 일부 사례를 되살릴 여지는 있었다. 하지만 마감 기한이 정해지지 않은 상황에서 기존 답변 품질을 유지하는 일이 우선이었다. 결국 `nano` 튜닝에 시간을 쏟기보다 처리해야 할 다른 핵심 기능 개발을 진행하는 쪽을 택했다. 절반 가까운 메모리 절감 이점에도 교체를 보류하고 `BGE v2-m3`를 GPU에 유지했다. 이에 따라 `KURE-v3` 임베딩은 GPU 충돌을 피해 CPU에서 실행하는 구조가 확정됐다. *(CPU 환경에서 신규 문서를 4개씩 끊어 커밋하는 색인 루프는 2편에서 다루었다.)*
