## 1. 검색기 구조와 메타데이터

대규모 지식 베이스를 다루는 검색기는 단일 알고리즘만으로 모든 질문에 대응하기 어렵다. 사용자는 고유 명사나 제품 코드를 정확히 입력하기도 하고, 모호한 자연어로 의미를 질문하기도 한다. 또한 사내 문서에는 접근 권한이나 발행 일자 같은 엄격한 비즈니스 규칙이 존재한다.

따라서 현대 RAG 시스템의 검색기(Retriever)는 서로 다른 세 가지 기법을 결합한 하이브리드 구조를 사용한다. 정확한 단어를 대조하는 키워드 검색, 문맥의 의미를 파악하는 시맨틱 검색, 그리고 엄격한 조건을 판별하는 메타데이터 필터링이 유기적으로 맞물려 돌아간다.

![하이브리드 리트리버 아키텍처 개요](/images/rag/module2/hybrid_search_pipeline.png)

위 다이어그램처럼 사용자의 질의가 입력되면 시스템은 키워드 검색과 시맨틱 검색을 동시에 수행한다. 두 검색기는 지식 베이스를 탐색하여 각각 20~50건 내외의 후보 문서 목록을 추출한다. 키워드 검색은 질의의 단어가 직접 포함된 문서를 찾고, 시맨틱 검색은 단어가 달라도 질문의 의도와 의미가 유사한 문서를 수집한다. 추출된 두 후보 목록은 검색 방식의 차이로 인해 문서의 순위가 서로 다르게 매겨진다.

이 과정에서 각 후보 목록에 메타데이터 필터링(Metadata Filtering)이 적용된다. 메타데이터는 제목, 작성자, 발행일, 열람 권한처럼 본문 외부에 부여된 구조화된 속성이다. 메타데이터 필터는 SQL의 `WHERE` 절처럼 엄격한 조건(Rigid criteria)으로 문서를 선별한다. 예를 들어 사내 지식 베이스에서 일반 직원이 질문을 던지면, 시스템은 사용자 권한을 확인하여 인사팀 전용 문서를 검색 대상에서 제외한다. 신문사 시스템이라면 무료 사용자에게 유료 구독 기사를 배제하는 식이다.

다이어그램을 자세히 보면 검색기가 문서를 먼저 찾은 뒤 필터로 걸러내는 사후 필터링(Post-filtering) 순서로 동작한다. 하지만 이 방식을 그대로 적용하면 결과 부족(Under-retrieval) 문제가 나타난다. 앞선 사내 챗봇 예시에서, 검색기가 뽑은 상위 50건 중 대다수가 타 부서 문서라면 어떻게 될까? 인사팀 필터를 거치고 남는 유효 문서는 1~2건에 불과해져 요청한 개수(`top_k`)를 채우지 못한다.

이 때문에 검색 누락을 방지하려면 조건을 만족하는 문서군을 먼저 한정해 두고 검색을 수행하는 사전 필터링(Pre-filtering)을 주로 사용한다. 나아가 최신 벡터 데이터베이스는 인덱스 탐색 과정에서 조건을 실시간으로 검증하는 단일 단계 필터링을 표준으로 채택한다.

이처럼 메타데이터 필터링은 검색 대상 범위를 엄격하게 통제하지만, 조건 일치(True/False)만 가려낼 뿐 질문과의 의미적 연관성 순위(Ranking)는 계산하지 못한다. 결국 사용자가 원하는 문서를 정확히 찾아내려면 본문을 실질적으로 평가하는 키워드 검색과 시맨틱 검색이 뒷받침되어야 한다. 이제 두 검색 축 중 첫 번째인 키워드 매칭과 BM25 알고리즘의 내부 원리를 살펴본다.

## 2. 키워드 검색과 BM25 원리

### 단어 출현 빈도와 길이 편향의 발생 원리

키워드 검색(Keyword Search)은 질문에 포함된 단어가 문서에 직접 등장하는지 대조하는 방식이다. 수십 년간 정보 검색 시스템의 표준으로 쓰여온 검증된 기술이다.

검색 대상 텍스트를 처리하려면 문서를 수치 벡터로 변환해야 한다. 시스템의 전체 어휘 사전을 기준으로 문서마다 각 단어가 등장한 횟수를 기록한다. 대부분의 단어 위치가 0으로 채워지므로 이를 희소 벡터(Sparse Vector)라 부른다.

초기 검색 시스템은 질의 단어의 출현 횟수인 단어 빈도(Term Frequency, TF)를 점수로 사용했다. 하지만 단순 빈도 합산은 심각한 왜곡을 낳는다. 

예를 들어 `"pizza oven"`이라는 질문에 대해 두 문서가 있다고 가정한다.
- 문서 1: "Homemade pizza in oven is better than frozen pizza" (pizza 2회, oven 1회 ➔ **TF 합계 3점**)
- 문서 2: "Wood-fired oven is a better oven than a stone oven for cooking pizza" (pizza 1회, oven 3회 ➔ **TF 합계 4점**)

단순 TF 점수만 보면 문서 2가 더 관련성이 높아 보인다. 하지만 문서 2는 피자 레시피가 아니라 단순히 문장이 길어서 `oven`이라는 단어가 반복되었을 뿐이다. 길이가 긴 문서가 무조건 유리해지는 문서 길이 편향이 발생한다. 여기에 'the'나 'is'처럼 의미 없는 불용어가 빈번하게 나타나 점수를 왜곡하는 문제도 겹친다.

이러한 문제를 해결하기 위해 역문서 빈도(Inverse Document Frequency, IDF)가 도입되었다. IDF는 단어가 전체 문서군에서 얼마나 희귀하게 등장하는지를 수치화한다. 전체 문서 수($N$)를 해당 단어가 포함된 문서 수($\text{DF}$)로 나눈 뒤 로그를 취한다.

$$\text{IDF}(q) = \ln\left(\frac{N}{\text{DF}(q)}\right)$$

모든 문서에 흔하게 등장하는 일반 단어는 IDF 값이 0에 가깝게 낮아진다. 반면 특정 문서에만 드물게 나타나는 핵심 명사는 높은 가중치를 얻는다. 여기에 문서 길이로 나누어 긴 문서의 일방적인 우세를 완화한 것이 전통적인 TF-IDF 방식이다.

### BM25 수식이 점수를 계산하는 수학적 원리

TF-IDF는 효과적인 기준선이었지만 여전히 두 가지 계산 원리상의 한계가 존재했다. 첫째, 단어 빈도(TF)가 증가할 때 점수가 정비례하여 선형으로 오른다는 점이다. 핵심 단어가 10번 등장할 때 점수가 $X$라면, 20번 등장하면 $2X$가 된다. 하지만 단어가 20번 나온 문서가 10번 나온 문서보다 정확히 2배 더 가치 있다고 보기는 어렵다. 둘째, 긴 문서에 대한 감점 기준이 너무 단순하여 유익한 장문 문서가 과도하게 낮은 점수를 받는다.

이 두 가지 결함을 정교한 수식으로 보완한 알고리즘이 BM25(Best Matching 25)다. BM25는 다음 공식으로 질의 $Q$에 대한 문서 $D$의 유사도 점수를 계산한다.

$$\text{Score}(D, Q) = \sum_{q \in Q} \text{IDF}(q) \cdot \frac{f(q, D) \cdot (k_1 + 1)}{f(q, D) + k_1 \cdot \left(1 - b + b \cdot \frac{|D|}{\text{avgdl}}\right)}$$

수식에서 $f(q, D)$는 문서 내 단어 출현 빈도이며, $|D|$는 문서의 단어 수, $\text{avgdl}$은 전체 문서의 평균 단어 수다. 이 수식이 동작하는 핵심은 두 개의 튜닝 파라미터 $k_1$과 $b$에 있다.

$k_1$은 단어 빈도 포화도(Term Frequency Saturation)를 제어한다. 수식의 분수 항을 보면 분자와 분모에 모두 $f(q, D)$가 들어있다. 단어 출현 횟수가 아무리 커져도 분수 항의 극한값은 $k_1 + 1$로 수렴한다. 따라서 단어가 반복될수록 추가 점수의 증가 폭이 완만하게 줄어든다. TF-IDF에서 10회 등장 시 $X$점이 20회 등장 시 $2X$가 되었다면, BM25에서는 약 $1.3X$점으로 수렴하며 단어 도배에 의한 점수 왜곡을 방어한다. $k_1$ 값은 통상 1.2에서 2.0 사이로 설정한다.

$b$는 문서 길이 정규화(Document Length Normalization)의 강도를 조절한다. 분모의 $\frac{|D|}{\text{avgdl}}$ 항에 주목하면, 문서 길이($|D|$)가 전체 평균($\text{avgdl}$)보다 길면 분모가 커져 점수가 깎이고, 짧으면 분모가 작아져 점수가 높아진다. $b=0$이면 문서 길이를 전혀 고려하지 않고, $b=1$이면 문서 길이에 정비례하여 엄격하게 감점한다.

TF-IDF의 단순 나눗셈 방식은 긴 문서에 지나치게 가혹하다. 예를 들어 60단어짜리 짧은 레시피 카드에 '초콜릿'이 3번 등장하면 비율은 5%다. 반면 6,000단어짜리 상세한 요리책 챕터에 '초콜릿'이 30번 등장해도 비율은 0.5%에 불과하다. TF-IDF는 단순 나눗셈으로 인해 30번이나 언급된 상세 요리책을 탈락시킨다. 반면 BM25는 분모의 $b$를 통해 문서 길이에 따른 감점의 한계 페널티를 완만하게 조절한다. 통상 알고리즘의 기본값으로 $b=0.75$를 설정하여 유익한 장문 문서가 과도하게 감점되지 않도록 완충한다.

### 파이썬 BM25의 3단계 파이프라인과 한계

파이썬 환경에서는 고속 연산에 최적화된 `bm25s` 라이브러리를 통해 이 과정을 구현할 수 있다. 검색 과정은 **토큰화 ➔ 색인 구축 ➔ 상위 문서 추출**의 세 단계로 나뉜다.

```python
import bm25s

# 1단계: 뉴스 데이터의 제목과 본문 요약을 결합한 코퍼스 생성 및 토큰화
corpus = [f"{x['title']} {x['description']}" for x in NEWS_DATA]
tokenized_corpus = bm25s.tokenize(corpus)

# 2단계: 역색인(Inverted Index) 테이블 빌드
retriever = bm25s.BM25(corpus=corpus)
retriever.index(tokenized_corpus)

# 3단계: 질문 토큰화 및 상위 k개 문서 인덱스 검색
def bm25_retrieve(query: str, top_k: int = 5) -> list[int]:
    tokenized_query = bm25s.tokenize(query)
    results, scores = retriever.retrieve(tokenized_query, k=top_k)
    
    # 검색된 문서 문자열을 원본 코퍼스 인덱스 번호로 매핑
    top_k_indices = [corpus.index(doc) for doc in results[0]]
    return top_k_indices
```

각 단계의 내부 동작은 다음과 같다.

1. **토큰화(`tokenize`)**: 문자열을 소문자로 변환하고 공백과 문장 부호를 제거하여 정제된 어휘 토큰 리스트로 쪼갠다.
2. **색인 구축(`index`)**: 단순 텍스트 저장이 아니라 메모리상에 **역색인(Inverted Index) 룩업 테이블**을 빌드한다. 각 단어마다 어느 문서에 몇 번 등장했는지를 기록하는 포스팅 리스트(Posting List)를 생성한다. 동시에 전체 문서 수($N$), 단어별 IDF, 개별 문서 길이($|D|$), 평균 문서 길이($\text{avgdl}$)를 사전에 계산해 둔다.
3. **상위 문서 추출(`retrieve`)**: 질문이 들어오면 질문 속 토큰들을 키로 삼아 역색인에서 해당 단어의 포스팅 리스트만 즉시 조회한다. 질문 단어가 한 번이라도 등장한 문서들만을 대상으로 BM25 공식을 적용해 점수를 누적(Scoring Accumulator)한다. 마지막으로 힙(Heap) 자료구조를 활용해 점수가 가장 높은 상위 `k`개의 문서 인덱스를 O(1)에 가깝게 추출한다.

BM25는 고유 명사, 제품 번호, 특수 용어를 검색할 때 매우 강력하고 신속하게 동작한다. 하지만 키워드 검색에는 근본적인 **어휘 불일치(Vocabulary Mismatch)** 문제가 존재한다. 

예를 들어 사용자가 '스마트폰'으로 질문했을 때, 문서에 '휴대폰'이라고 적혀 있다면 역색인의 단어 키가 일치하지 않는다. 두 단어가 사실상 동일한 대상을 의미하더라도, 해당 문서는 점수 계산 대상인 포스팅 리스트에 진입조차 하지 못하고 탈락한다.

이러한 철자 기반 매칭의 한계를 극복하려면 단어 표기를 넘어 문맥의 의미를 파악하는 기술이 필요하다. 다음 장에서는 문장을 고차원 의미 공간의 좌표로 변환하는 시맨틱 검색과 임베딩 모델의 원리를 알아본다.

## 3. 시맨틱 검색과 코사인 유사도

### 밀집 벡터와 대조 학습의 군집 원리

앞서 살펴본 키워드 검색은 단어의 형태가 일치해야만 동작한다. 질의에 '스마트폰'을 입력하면 문서에 '휴대폰'이 있어도 찾아내지 못한다. 또한 프로그래밍 언어 '파이썬'과 뱀의 일종인 '파이썬'처럼 동일한 단어가 서로 다른 문맥에서 쓰일 때도 이를 구분하지 못한다.

시맨틱 검색(Semantic Search)은 이러한 표기 차이를 넘어 문장 전체의 의미와 문맥을 대조한다. 텍스트를 고차원 공간상의 좌표로 변환하는 임베딩 모델(Embedding Model)을 기반으로 동작한다.

![단어 및 문장의 벡터 공간 임베딩](/images/rag/module2/embedding.png)

키워드 검색의 희소 벡터는 대부분 0으로 채워진 수만 차원의 배열이다. 반면 시맨틱 검색의 임베딩 벡터는 모든 차원이 연속적인 실수로 채워진 밀집 벡터(Dense Vector)다. 통상 384차원, 768차원, 혹은 1,536차원 이상의 고차원 연속 공간을 활용한다.

임베딩 모델이 의미를 파악하는 원리는 대조 학습(Contrastive Learning)에 있다. 모델은 앵커(Anchor), 긍정 예시(Positive Pair), 부정 예시(Negative Pair)로 구성된 대규모 데이터셋을 학습한다. 예를 들어 '좋은 아침'이라는 문장이 앵커라면, '안녕하세요'는 긍정 예시가 되고 '사자가 포효한다'는 부정 예시가 된다.

초기 모델의 파라미터는 무작위로 초기화되어 텍스트를 무의미한 난수 좌표에 배치한다. 학습이 진행되면서 손실 함수는 긍정 예시의 벡터 거리를 가깝게 당기고, 부정 예시의 벡터 거리를 멀리 밀어낸다. 수백만 건의 데이터를 반복 갱신하면 의미가 비슷한 문장들이 고차원 공간 내에서 자연스럽게 특정 군집(Cluster)을 형성한다.

### 유클리드 거리의 한계와 코사인 방향 측정

임베딩 모델을 통해 문서를 벡터로 변환했다면 질문 벡터와의 유사도를 계산해야 한다. 가장 직관적인 척도는 고등학교 기하학에서 다루는 유클리드 거리(Euclidean Distance)다. 피타고라스 정리에 따라 두 점 사이의 최단 직선 거리를 측정한다.

$$d(u, v) = \sqrt{\sum_{i=1}^{n} (u_i - v_i)^2}$$

하지만 유클리드 거리는 고차원 벡터 검색에서 두 가지 기하학적 한계를 드러낸다. 첫째는 고차원의 저주다. 차원이 수백 개로 늘어나면 공간 내 모든 벡터 사이의 거리가 서로 비슷해지면서 변별력이 떨어진다. 둘째는 문서 길이에 따른 벡터 크기 왜곡이다. 동일한 주제를 다루더라도 단어 수가 많은 장문 문서는 성분 값이 누적되어 원점으로부터 거리가 길어진다.

![유클리드 거리와 코사인 유사도의 방향 비교](/images/rag/module2/cosine.png)

위 그림처럼 벡터 $A=[10, 10]$과 벡터 $B=[100, 100]$을 비교해 본다. 두 벡터는 원점으로부터의 직선 거리가 매우 멀어서 유클리드 거리 계산 시 완전히 다른 문서로 판정된다. 하지만 두 벡터가 가리키는 방향은 정확히 동일하다. 즉, 다루는 주제와 내용의 맥락은 같고 분량만 다를 뿐이다.

이러한 크기 왜곡을 배제하기 위해 검색기에서는 코사인 유사도(Cosine Similarity)를 표준 척도로 사용한다. 코사인 유사도는 두 벡터의 크기를 각각의 노름($L_2$ Norm)으로 나누어 1로 정규화한 뒤, 두 벡터 사이의 사잇각($\theta$)을 측정한다.

$$\text{Cosine}(u, v) = \frac{u \cdot v}{\|u\| \|v\|} = \frac{\sum_{i=1}^{n} u_i v_i}{\sqrt{\sum_{i=1}^{n} u_i^2} \sqrt{\sum_{i=1}^{n} v_i^2}}$$

코사인 유사도의 결괏값은 $-1$부터 $1$ 사이로 정규화된다. 방향이 완전히 일치하면 사잇각이 $0^\circ$가 되어 최댓값 $1.0$을 갖는다. 직교하여 연관성이 없으면 $0$, 방향이 정반대면 $-1$이 된다. 따라서 문서의 길이에 휘둘리지 않고 순수한 의미적 지향점만을 객관적으로 비교할 수 있다.

벡터 간 유사도를 측정하는 또 다른 수학적 척도로는 내적(Dot Product)이 있다. 내적($u \cdot v = \|u\| \|v\| \cos \theta$)은 한 벡터를 다른 벡터 위로 정사영(Projection)한 길이와 기준 벡터 크기의 곱이다. 만약 두 벡터의 크기를 각각 1로 정규화해 두면($\|u\|=\|v\|=1$), 분모가 1이 되어 내적 연산 결과는 코사인 유사도와 수학적으로 완전히 일치한다. 벡터 데이터베이스가 분모 나눗셈 연산을 생략하고 고속 내적 연산만으로 코사인 유사도를 빠르게 계산하는 이유가 여기에 있다.

또한 실습 랩에서 관찰되듯, 동일한 질문에 대해 유클리드 거리 기준으로는 가장 가까운 문서가 코사인 유사도 기준으로는 순위가 밀리는 순위 역전(Rank Inversion) 현상이 일어난다. 유클리드는 공간 내 절대 거리를 측정하지만, 코사인 유사도는 오직 의미의 지향 각도만을 측정하기 때문이다.

### 넘파이 기반 유사도 연산과 입력 길이 한계

코사인 유사도가 계산되는 구체적인 원리를 순수 넘파이(NumPy) 코드로 확인해 본다. 강의 실습 랩에서는 기하학 수식을 다음과 같이 구현한다.

```python
import numpy as np

def cosine_similarity(v1, array_of_vectors):
    """기준 벡터와 복수 벡터 간의 코사인 유사도를 계산한다."""
    v1 = np.array(v1)
    similarities = []
    
    # 단일 벡터 입력 시 2차원 리스트로 통일
    if len(np.shape(array_of_vectors)) == 1:
        array_of_vectors = [array_of_vectors]
        
    for v2 in array_of_vectors:
        v2 = np.array(v2)
        # 두 벡터의 내적(Dot Product) 연산
        dot_product = np.dot(v1, v2)
        
        # 벡터 크기(L2 Norm) 계산
        norm_v1 = np.linalg.norm(v1)
        norm_v2 = np.linalg.norm(v2)
        
        # 크기를 배제하고 방향의 사잇각(Cosine) 도출
        similarity = dot_product / (norm_v1 * norm_v2)
        similarities.append(similarity)
        
    return [float(x) for x in similarities]
```

함수는 질문 벡터 `v1`과 코퍼스 내 문서 벡터들의 배열 `array_of_vectors`를 입력받는다. 각 문서 벡터 `v2`마다 `np.dot`으로 내적을 구한다. 그리고 `np.linalg.norm`으로 계산한 두 벡터 크기의 곱으로 나누어 코사인 유사도를 산출한다. 계산된 유사도 점수로 문서를 내림차순 정렬하면 질문과 의미가 가장 가까운 상위 `k`개 문서를 반환할 수 있다.

그러나 시맨틱 검색만으로 리트리버를 운영할 때도 주의해야 할 물리적 제약이 존재한다. 바로 임베딩 모델의 최대 시퀀스 길이(Max Sequence Length) 한계다. 

실습에 사용된 `bge-base-en-v1.5` 같은 오픈소스 임베딩 모델은 처리 가능한 토큰 한도가 512토큰 내외로 제한된다. 수십 페이지에 달하는 보고서나 문서를 임베딩 모델에 그대로 전달하면, 허용 한도를 초과한 후미 문장들은 예고 없이 잘려 나간다(Truncation). 

잘려 나간 본문의 정보는 벡터 좌표에 전혀 반영되지 않는다. 사용자가 문서 후반부 내용을 질문하면, 질문 벡터는 문서 벡터와 전혀 다른 위치를 가리켜 검색에서 누락된다. 이 한계를 극복하기 위해 긴 문서를 적절한 단위로 쪼개는 청킹(Chunking) 기술이 필요해진다.

아울러 임베딩 모델을 다룰 때는 두 가지 구조적 원칙과 한계를 함께 고려해야 한다. 

첫째, 서로 다른 임베딩 모델로 생성한 벡터는 절대 비교할 수 없다. 임베딩 모델마다 대조 학습 초기 난수 상태에서 독자적인 공간 좌표계를 형성하기 때문이다. 차원 수가 같더라도 모델 A로 만든 질의 벡터와 모델 B로 만든 문서 벡터를 대조하는 것은 무의미하다. 따라서 RAG 시스템에서는 질문과 문서를 반드시 동일한 임베딩 모델로 인코딩해야 한다.

둘째, 임베딩 모델의 동시 출현(Co-occurrence) 편향이다. 모델은 768차원 공간(PCA 기법으로 2차원 축소 관찰 가능)에 의미 군집을 형성할 때, 객관적 사실(Fact)이 아니라 말뭉치에서 단어들이 함께 등장한 문맥적 빈도를 학습한다. 실습 랩에서 '봄철 여행지 추천'을 질문했을 때 사실상 더 적합한 '교토의 벚꽃'보다, 말뭉치에서 '여행지'와 자주 함께 쓰인 '산토리니'가 더 높은 코사인 점수를 얻는 왜곡이 관찰된다.

이처럼 시맨틱 검색 단독으로는 단어의 팩트 매칭을 완벽히 보장할 수 없으며, 고유 명사나 제품 코드 매칭에서는 BM25보다 정확도가 떨어진다. 따라서 정확한 단어 매칭과 의미적 문맥 파악을 모두 확보하려면 BM25의 키워드 검색 결과와 임베딩 모델의 시맨틱 검색 결과를 결합해야 한다. 다음 장에서는 서로 점수 척도가 다른 두 검색 결과를 하나의 순위로 병합하는 하이브리드 검색과 RRF 알고리즘을 살펴본다.

## 4. 하이브리드 검색과 RRF 원리

### 이종 점수 체계와 단순 합산의 한계

하이브리드 검색의 핵심은 키워드 검색기(BM25)와 시맨틱 검색기(임베딩 모델)가 반환한 두 후보 목록을 하나의 통합 순위로 병합하는 작업이다. 하지만 서로 다른 검색 알고리즘의 원시 점수(Raw Score)를 직접 비교하거나 더하는 방식은 심각한 점수 왜곡을 유발한다.

두 알고리즘의 점수 척도(Scale)와 값의 분포가 완전히 다르기 때문이다. 시맨틱 검색의 코사인 유사도는 $-1.0$에서 $1.0$ 사이로 정규화된다. 통상 유사한 문서라도 $0.6$에서 $0.85$ 수준의 좁은 실수 범위에 몰린다. 반면 BM25 점수는 단어 빈도와 문서 길이에 따라 $0$부터 수십, 수백 점 이상으로 상한선 없이 발산한다.

만약 두 점수를 단순히 더한다면(Linear Combination), 절대 수치가 압도적으로 큰 BM25 점수가 최종 순위를 완전히 지배하게 된다. 코사인 유사도가 아무리 정교하게 문맥을 파악했더라도 순위에 거의 영향을 주지 못한다.

최소-최대 정규화(Min-Max Scaling)로 점수 범위를 맞추려 해도 문제가 남는다. 질의마다 문서 점수의 분포 형태가 매번 달라지기 때문에, 정규화된 점수의 상대적 가치를 일관되게 보정하기 어렵다. 따라서 점수의 절대적인 크기를 배제하고, 각 검색기 내부에서 매겨진 상대적인 순위(Rank)만을 추출하여 결합하는 알고리즘이 필요하다.

### RRF 수식과 파라미터 제어 메커니즘

이러한 점수 척도 불일치를 해결하기 위해 역순위 융합(Reciprocal Rank Fusion, RRF) 알고리즘을 사용한다. RRF는 각 검색기에서 문서가 기록한 순위의 역수(Reciprocal Rank)를 계산하여 누적한다.

$$\text{RRF\_Score}(d \in D) = \sum_{m \in M} \frac{1}{K + r_m(d)}$$

수식에서 $M$은 결합할 검색기 집합(키워드 검색, 시맨틱 검색)이며, $r_m(d)$는 검색기 $m$에서 문서 $d$가 차지한 순위다. 순위는 1위부터 시작한다($r \ge 1$).

수식의 핵심 동작은 순위가 높을수록(숫자가 작을수록) 분모가 작아져 더 큰 점수를 획득하는 것이다. 두 검색기 모두에서 상위권을 차지한 문서는 두 번의 점수 가산을 받아 최종 순위의 최상단으로 이동한다. 한쪽 검색기에서만 높은 순위를 차지했더라도, 다른 목록의 하위권 문서들보다 높은 점수를 얻을 수 있다.

수식에서 분모에 더해지는 상수 $K$는 순위 간 점수 격차를 조절하는 스무딩(Smoothing) 파라미터다. $K=0$인 극단적인 상황을 가정해 본다. 1위 문서의 점수는 $\frac{1}{1}=1.0$이지만, 10위 문서의 점수는 $\frac{1}{10}=0.1$로 줄어든다. 점수 차이가 무려 10배에 달한다. 이 경우 특정 검색기에서 우연히 1위를 차지한 문서 하나가 전체 통합 순위를 지나치게 독점한다.

반면 강의 슬라이드와 표준 구현처럼 $K=50$ 혹은 $K=60$을 적용하면 격차가 완화된다. $K=50$일 때 1위 문서의 점수는 $\frac{1}{51} \approx 0.0196$이고, 10위 문서는 $\frac{1}{60} \approx 0.0166$이다. 점수 차이가 약 1.18배(1.2배)로 줄어든다. 1위의 가치는 여전히 인정하되, 단일 검색기의 순위 편향이 전체 결과를 지배하지 않도록 완충한다.

시스템의 목적에 따라 키워드와 시맨틱의 중요도를 다르게 부여해야 할 때는 가중치 파라미터 $\beta$를 도입한다.

$$\text{RRF\_Score}(d) = (1 - \beta) \cdot \frac{1}{K + r_{\text{bm25}}(d)} + \beta \cdot \frac{1}{K + r_{\text{semantic}}(d)}$$

예를 들어 특수 제품명이나 고유 명사 매칭이 중요하다면 $\beta$를 낮추어 BM25에 가중치를 둔다. 반대로 자연어 대화의 의도 파악이 중심이라면 $\beta=0.7$ 혹은 $0.8$을 설정하여 시맨틱 검색의 비중을 높인다.

### 파이썬 RRF 구현과 증강 프롬프트 조립

강의 프로그래밍 과제에서 다룬 RRF 로직은 파이썬 딕셔너리를 활용해 순위를 점수로 누적한다.

```python
def reciprocal_rank_fusion(list1: list[int], list2: list[int], top_k: int = 5, K: int = 60) -> list[int]:
    """두 검색기에서 추출된 문서 인덱스 목록을 RRF 알고리즘으로 결합한다."""
    rrf_scores = {}

    # 두 검색 결과 목록을 순회하며 순위 역수 점수 누적
    for lst in [list1, list2]:
        for rank, doc_idx in enumerate(lst, start=1):
            if doc_idx not in rrf_scores:
                rrf_scores[doc_idx] = 0.0
            # 1 / (rank + K) 공식 적용
            rrf_scores[doc_idx] += 1.0 / (rank + K)

    # 누적된 RRF 점수를 기준으로 문서 인덱스를 내림차순 정렬
    sorted_docs = sorted(rrf_scores.keys(), key=lambda doc: rrf_scores[doc], reverse=True)

    # 최종 상위 top_k 문서 인덱스 반환
    return sorted_docs[:top_k]
```

코드의 동작 과정은 다음과 같다.
1. `enumerate(lst, start=1)`을 통해 0번 인덱스가 아닌 1위부터 시작하는 순위 번호를 부여한다.
2. 각 문서 번호(`doc_idx`)를 키로 삼아 $\frac{1}{\text{rank} + K}$ 점수를 딕셔너리에 합산한다. 두 목록에 중복으로 포함된 문서는 자연스럽게 점수가 누적된다.
3. `sorted` 함수로 누적 점수가 높은 순으로 정렬한 뒤, 요청한 개수(`top_k`)만큼 잘라내어 최종 인덱스를 추출한다.

추출된 상위 `top_k` 문서들은 원본 데이터 저장소에서 제목, 본문, 발행일자 같은 메타데이터와 결합하여 LLM이 이해할 수 있는 증강 프롬프트로 조립된다.

```python
def build_augmented_prompt(query: str, retrieved_docs: list[dict]) -> str:
    """검색된 문서 목록을 포맷팅하여 LLM 입력용 증강 프롬프트를 조립한다."""
    formatted_context = []
    
    for doc in retrieved_docs:
        context_entry = (
            f"Title: {doc['title']}\n"
            f"Published: {doc['published_at']}\n"
            f"Content: {doc['description']}\n"
            f"URL: {doc['url']}"
        )
        formatted_context.append(context_entry)
        
    context_block = "\n---\n".join(formatted_context)
    
    return (
        f"Answer the user query based on the following verified information.\n\n"
        f"Context Information:\n{context_block}\n\n"
        f"User Query: {query}"
    )
```

이로써 키워드 매칭과 시맨틱 유사도, 메타데이터 필터링이 모두 반영된 균형 잡힌 근거 문서가 LLM에 제공된다. 하지만 검색 파이프라인의 $K$, $\beta$, $top\_k$ 같은 하이퍼파라미터를 튜닝하려면, 검색기가 실제로 얼마나 정확한 문서를 가져왔는지 객관적인 수치로 측정해야 한다. 다음 장에서는 검색 성능을 정량화하는 핵심 평가 지표들을 살펴본다.

## 5. 검색 성능 지표와 평가 방법

### 정답셋과 정밀도·재현율의 상충 관계

검색 파이프라인을 구축한 뒤에는 검색기가 실제로 유효한 문서를 올바르게 찾아내는지 객관적으로 평가해야 한다. 검색 품질을 측정하려면 세 가지 기본 요소가 갖추어져야 한다.

1. **평가 질의(Prompt)**: 시스템에 입력할 테스트 질문 집합이다.
2. **검색 순위 목록(Ranked Results)**: 질의에 대해 검색기가 점수를 매겨 반환한 문서 목록이다.
3. **정답셋(Ground Truth)**: 지식 베이스 전체에서 해당 질의와 실질적으로 연관된 정답 문서들의 목록이다.

정답셋이 사전에 라벨링되어 있어야 검색 결과의 정확성을 수학적으로 검증할 수 있다. 정보 검색에서 가장 널리 쓰이는 두 가지 기본 척도는 정밀도(Precision)와 재현율(Recall)이다. 상위 $K$개의 결과를 평가할 때 수식은 다음과 같다.

$$\text{Precision@K} = \frac{\text{Relevant Retrieved}}{K}$$

$$\text{Recall@K} = \frac{\text{Relevant Retrieved}}{\text{Total Relevant}}$$

정밀도는 검색기가 가져온 결과 중 실제 정답이 얼마나 포함되었는지를 측정한다. 관련 없는 문서를 많이 섞을수록 감점된다. 반면 재현율은 지식 베이스에 존재하는 전체 정답 중 검색기가 몇 개나 놓치지 않고 찾아냈는지를 측정한다. 정답 문서를 빠뜨릴수록 감점된다.

강의의 구체적인 수치 예시를 통해 두 지표의 상충 관계(Trade-off)를 살펴본다. 전체 지식 베이스에 특정 질의와 관련된 정답 문서가 총 10건 존재한다고 가정한다.

- **1차 실행**: 검색기가 12건의 문서를 반환했고, 그중 8건이 정답이었다.
  - $\text{Precision} = \frac{8}{12} \approx 66.7\%$
  - $\text{Recall} = \frac{8}{10} = 80.0\%$
- **2차 실행**: 검색 범위를 넓혀 15건의 문서를 반환했고, 그중 9건이 정답이었다.
  - $\text{Precision} = \frac{9}{15} = 60.0\%$
  - $\text{Recall} = \frac{9}{10} = 90.0\%$

2차 실행에서는 문서를 3건 더 가져와 정답을 1건 더 찾아냈다. 그 결과 재현율은 $80\%$에서 $90\%$로 상승했다. 하지만 무관한 문서 2건이 함께 유입되면서 정밀도는 $66.7\%$에서 $60.0\%$로 떨어졌다. 이처럼 검색 문서 수($K$)를 늘리면 재현율을 높일 수 있지만 정밀도는 희생되는 상충 관계가 발생한다.

실제 20 Newsgroups 데이터셋을 활용한 비채점 랩 실습에서도 이 상충 관계가 명확하게 관찰된다.
- $K=5$일 때 $\text{Precision@5}$는 $0.80\sim1.00$으로 최상위 문서 대부분이 정답이다. 하지만 수백 건의 전체 정답 중 극히 일부만 가져오므로 $\text{Recall@5}$는 약 $1\%$에 그친다.
- $K=20$으로 늘리면 $\text{Recall}$은 약 $3\%$로 증가하지만 $\text{Precision}$은 $0.65\sim0.80$으로 낮아진다.
- $K=50$에서는 $\text{Recall}$이 $5\sim8\%$까지 오르지만 $\text{Precision}$은 $0.50\sim0.66$까지 떨어진다.

여기서 중요한 점은 RAG 파이프라인이 추구하는 목표다. RAG의 목적은 지식 베이스의 모든 문서를 다 긁어오는 것(Recall 100%)이 아니다. LLM의 한정된 컨텍스트 창 내에서 가장 확실하고 노이즈 없는 핵심 근거(High Precision)를 전달하는 것이 핵심이다. 전체 정답을 다 가져오기 위해 $K$를 수백 단위로 늘리면 무관한 문서가 대거 유입되어 LLM이 환각을 일으킬 위험이 커진다. 따라서 RAG 시스템에서는 통상 정밀도를 높게 유지할 수 있는 $K=5\sim20$ 범위를 표준적인 검색 단위로 채택한다.

### 순위 품질을 반영하는 MAP@K와 MRR

$\text{Precision@K}$는 상위 $K$개 내에 정답이 몇 개 포함되었는지만 계산할 뿐, 문서가 몇 위에 위치했는지는 구분하지 못한다. 예를 들어 $K=5$일 때 1위와 2위에 정답이 있는 경우와, 4위와 5위에 정답이 있는 경우는 모두 정밀도 $40\%$로 동일하게 평가된다. 하지만 언어 모델 입장에서는 정답 문서가 상단에 먼저 노출되는 것이 훨씬 유리하다.

이러한 순위 위치를 평가에 반영하기 위해 평균 정밀도(Average Precision, AP)를 사용한다. $\text{AP@K}$는 상위 $K$개의 순위를 차례로 내려가면서 정답 문서가 나타나는 위치마다의 정밀도를 계산한 뒤, 이 값들의 평균을 구한다.

강의 슬라이드에 제시된 6개 문서 검색 결과 예시를 통해 계산 과정을 확인해 본다.

| 순위 ($k$) | 문서 관련 여부 | 해당 순위까지의 $\text{Precision@}k$ | 계산 근거 |
| :---: | :---: | :---: | :--- |
| **1위** | 관련 (정답) | **$1.0$** | 1개 중 1개 일치 ($\frac{1}{1}$) |
| 2위 | 무관 | $0.5$ | 2개 중 1개 일치 ($\frac{1}{2}$) |
| 3위 | 무관 | $0.33$ | 3개 중 1개 일치 ($\frac{1}{3}$) |
| **4위** | 관련 (정답) | **$0.5$** | 4개 중 2개 일치 ($\frac{2}{4}$) |
| **5위** | 관련 (정답) | **$0.6$** | 5개 중 3개 일치 ($\frac{3}{5}$) |
| 6위 | 무관 | $0.5$ | 6개 중 3개 일치 ($\frac{3}{6}$) |

$\text{AP@6}$을 계산할 때는 정답 문서가 위치한 행(1위, 4위, 5위)의 정밀도만 합산한다.

$$\text{정밀도 합} = 1.0 + 0.5 + 0.6 = 2.1$$

이 합산값을 검색된 상위 6개 내 총 정답 문서 수(3건)로 나눈다.

$$\text{AP@6} = \frac{2.1}{3} = 0.7$$

만약 무관한 문서가 상위권에 끼어들면 그 아래에 위치한 모든 정답 문서의 $\text{Precision@}k$가 함께 깎인다. 따라서 정답을 최상단에 집중적으로 배치할수록 높은 AP 점수를 얻는다. 여러 평가 질의에 대해 계산된 AP 값들을 전체 평균 낸 지표를 **MAP@K(Mean Average Precision@K)**라 부른다.

또 다른 핵심 순위 지표는 **MRR(Mean Reciprocal Rank)**이다. MRR은 반환된 목록 전체에서 '가장 첫 번째 정답 문서'가 등장한 순위의 역수(Reciprocal Rank)를 측정한다.

$$\text{RR} = \frac{1}{\text{Rank}_1}$$

여기서 $\text{Rank}_1$은 특정 질문에 대해 첫 번째 정답 문서가 나타난 순위 번호다. 중요한 점은 MRR이 동일한 질문을 여러 번 반복 검색하는 지표가 아니라는 사실이다. 검색기는 같은 질문에 항상 같은 결과를 반환하므로 단순 반복은 무의미하다.

MRR은 사전에 준비한 평가 질문 데이터셋($Q$)에 포함된 서로 다른 모든 질문마다의 $\text{RR}$을 구한 뒤 산술 평균을 계산한다.

$$\text{MRR} = \frac{1}{|Q|} \sum_{i=1}^{|Q|} \frac{1}{\text{Rank}_i}$$

예를 들어 4개의 서로 다른 테스트 질문으로 구성된 데이터셋($|Q|=4$)에서 각 질문의 첫 정답 문서가 1위, 3위, 6위, 2위에 위치했다고 가정한다.

- 질문 1: 1위 등장 ➔ $\text{RR}_1 = \frac{1}{1} = 1.0$
- 질문 2: 3위 등장 ➔ $\text{RR}_2 = \frac{1}{3} \approx 0.33$
- 질문 3: 6위 등장 ➔ $\text{RR}_3 = \frac{1}{6} \approx 0.17$
- 질문 4: 2위 등장 ➔ $\text{RR}_4 = \frac{1}{2} = 0.5$

이 네 질문에 대한 평균을 구하면 최종 $\text{MRR}$은 다음과 같다.

$$\text{MRR} = \frac{1.0 + 0.33 + 0.17 + 0.5}{4} = \frac{2.0}{4} = 0.5$$

MRR은 단일 사실 확인처럼 사용자가 가장 처음 마주치는 정답 정보가 얼마나 상위에 배치되었는지를 빠르고 직관적으로 검증한다.

### RAG 관점에서의 메트릭 종합과 튜닝 기준

RAG 파이프라인에서는 단일 지표에만 의존하지 않고 각 메트릭의 역할을 유기적으로 결합하여 검색기를 최적화한다.

1. **Recall@K (기본 기반)**: RAG 시스템에서 가장 먼저 확보해야 할 필수 지표다. 외부 지식 베이스의 핵심 근거가 검색 결과에서 누락되면 언어 모델은 필요한 정보를 전혀 참조할 수 없다. 따라서 충분한 문맥 확보를 위해 일정한 수준 이상의 재현율을 확보해야 한다.
2. **Precision@K 및 MAP@K (노이즈 방어)**: 재현율을 올리기 위해 검색 개수($K$)를 무작정 늘리면 불필요한 잡음 문서가 유입된다. 이는 LLM의 제한된 컨텍스트 길이를 낭비하고, 모델이 엉뚱한 정보에 주의를 기울여 환각(Hallucination)을 생성할 위험을 높인다. MAP@K는 핵심 정답이 프롬프트 상단에 배치되도록 보장한다.
3. **MRR (초기 도달 속도)**: 명확한 단일 답변이 필요한 질의에서 최상단 1~2개 문서 내에 정확한 근거가 들어왔는지 검증하는 기준으로 활용된다.

이러한 지표들은 하이브리드 검색 파이프라인의 하이퍼파라미터를 결정하는 명확한 기준이 된다. 

예를 들어 RRF 공식에서 키워드와 시맨틱의 가중치($\beta$)를 조절할 때, 평가셋에 대해 $\text{Recall@5}$와 $\text{MAP@5}$를 함께 측정한다. 특정 데이터셋에서 $\beta=0.7$일 때가 $\beta=0.3$일 때보다 $\text{MAP@5}$가 $15\%$ 이상 높게 측정된다면, 시맨틱 검색의 비중을 높이는 설정이 타당하다는 정량적 근거를 얻을 수 있다.

이로써 2편에서는 키워드 매칭(BM25)과 시맨틱 임베딩, 메타데이터 필터링의 상호보완적 결합 원리를 살펴보고, RRF 병합과 검색 평가 지표(Precision, Recall, MAP, MRR)를 정립했다. 

하지만 수백만에서 수억 건에 달하는 대규모 텍스트를 다룰 때는 모든 문서 벡터를 순차 비교하는 방식이 심각한 지연 시간(Latency) 문제를 일으킨다. 다음 3편에서는 대규모 고차원 벡터를 초고속으로 검색하는 **벡터 데이터베이스(Vector DB)**와 **근사 최근접 탐색(ANN)** 알고리즘, 그리고 장문 문서를 최적의 단위로 분할하는 **청킹(Chunking)** 기법을 다룬다.
