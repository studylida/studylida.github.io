> 컨테이너와 오토스케일링 환경에서 서비스 인스턴스의 IP는 수시로 바뀐다. 이 글은 동적 주소 탐색을 위한 서비스 디스커버리의 탄생 배경, DNS와 L4/L7의 한계, 클라이언트와 서버 사이드 패턴, 전파 지연 대응을 정리한다.

## 1. 정적 주소에서 동적 환경으로

컴포넌트 간 통신 방식의 변화는 백엔드 아키텍처의 주소 관리 방식을 근본적으로 바꾸어 놓았다.

단일 프로세스로 모든 비즈니스 로직이 기동되던 모놀리스(Monolith) 환경에서는 모듈 간 통신이 단순했다. 한 클래스가 다른 모듈 기능을 호출할 때 애플리케이션 힙 메모리 상의 주소를 참조하는 직접 함수 호출(`userService.findUserById(id)`)에 불과했다. 컴파일러와 링커, OS 가상 메모리 관리자가 주소 바인딩을 보장하므로 네트워크 지연이나 대상 주소 유실은 고려 대상이 아니었다.

```mermaid
flowchart LR
    subgraph Monolith ["모놀리스 환경"]
        M1["주문 모듈"] -->|"인메모리 함수 호출<br/>(메모리 참조, 0ms)"| M2["결제 모듈"]
    end

    subgraph StaticVM ["초기 분산 환경 (가상머신/베어메탈)"]
        V1["주문 서버"] -->|"고정 IP 직결<br/>(http://192.168.1.50:8080)"| V2["결제 서버<br/>(192.168.1.50)"]
    end
```

시스템이 물리적으로 분리된 초기 분산 환경(베어메탈 및 고정 가상머신)에서도 주소 해결은 여전히 정적인 방식으로 관리될 수 있었다. 서버 대수가 수 대에서 수십 대 수준이었고, 서버 한 대를 프로비저닝하고 IP를 할당받는 데 수 시간에서 수일이 걸렸기 때문이다. 엔지니어는 각 서버의 고정 IP를 `application.yml`이나 정적 프로퍼티 파일에 하드코딩해 두는 것만으로도 서비스를 안정적으로 운영할 수 있었다.

그러나 클라우드 인프라와 컨테이너 가상화(Docker, Kubernetes)의 등장은 이러한 전제를 무효화했다.

```mermaid
flowchart TB
    subgraph DynamicCloud ["현대 클라우드/컨테이너 환경"]
        direction TB
        C1["HPA (오토스케일링)"] -->|"트래픽 폭증 시 신규 파드 급증"| D1["초당 수십 개 파드 생성"]
        C2["노드 장애 및 재스케줄링"] -->|"물리 노드 고장 시 다른 노드로 이동"| D2["새로운 사설 IP 무작위 할당"]
        C3["무중단 롤링 배포"] -->|"구버전 종료 후 신버전 투입"| D3["파드 수명 주기 수 분~수 시간"]
    end
```

현대 MSA 환경에서 서버 인스턴스는 더 이상 영속적인 물리 자산이 아닌, 필요에 따라 언제든 종료되고 재생성되는 일시적 인스턴스다. 
1. **잦은 스케일 아웃/인**: 트래픽 부하에 따라 Horizontal Pod Autoscaler(HPA)가 파드를 수시로 증감시킨다.
2. **동적 사설 IP 할당**: 파드가 재기동되거나 다른 워커 노드로 스케줄링될 때마다 네트워크 인터페이스에는 무작위 가상 IP(e.g., `10.244.3.52`)가 할당된다.
3. **짧아진 인스턴스 수명**: 배포 주기가 빨라지면서 하루에도 수십 번씩 인스턴스가 생성되고 종료된다.

이러한 환경에서 호출할 대상의 IP를 정적 설정 파일에 기록해 두는 것은 서비스 불능을 의미한다. 상대방 파드가 재시작되는 순간 기존 IP는 유효하지 않게 되고, 클라이언트는 타임아웃과 연결 거부 에러에 직면하게 된다.

## 2. 전통 DNS와 L4/L7의 한계

기존 인터넷을 지탱해 온 도메인 네임 시스템(DNS)과 하드웨어 로드밸런서(L4/L7)는 동적 컨테이너 환경의 주소 문제를 해결하기에 구조적 한계를 안고 있다.

새로운 인프라 컴포넌트를 도입하기 전에 먼저 던져야 할 질문이 있다. "이미 전 세계 인터넷의 주소를 해결하는 DNS나 대규모 트래픽 처리에 쓰이는 L4/L7 스위치를 내부 통신에 그대로 쓰면 안 되는가?" 결론부터 말하면 두 기술 모두 인스턴스가 수시로 바뀌는 마이크로서비스 내부(East-West) 통신을 감당하도록 설계되지 않았다.

### 1) DNS TTL의 근본적 딜레마
DNS는 도메인 이름(`api.example.com`)을 IP 주소로 매핑해 주는 전 세계적인 분산 디렉터리 시스템이다. 그러나 DNS에는 캐싱을 제어하는 **TTL(Time-To-Live)** 설정에 따른 트레이드오프가 존재한다.

```mermaid
flowchart TD
    subgraph Dilemma ["DNS TTL 트레이드오프 딜레마"]
        T1["TTL을 길게 설정할 경우<br/>(예: 60초 ~ 300초)"] --> R1["인스턴스 장애 시 Stale 캐시 유지<br/>→ 종료된 IP로 수 분간 트래픽 인입 (장애 발생)"]
        T2["TTL을 극단적으로 짧게 설정할 경우<br/>(예: 0초 ~ 1초)"] --> R2["모든 RPC마다 DNS 조회 발생<br/>→ DNS 서버(CoreDNS) CPU 고갈 및 응답 지연"]
    end
```

* **TTL이 길 때 (Stale Data)**: 특정 컨테이너가 예기치 않게 종료(Crash)되었을 때, 클라이언트는 로컬 DNS 캐시에 남아 있는 만료 전 IP로 계속 요청을 보낸다. 트래픽은 유실되고 대규모 서비스 장애로 이어진다.
* **TTL이 짧을 때 (Server Overload)**: 지연을 방지하기 위해 TTL을 0이나 1초로 낮추면, 수천 개의 마이크로서비스 인스턴스가 API를 호출할 때마다 네임서버로 DNS 질의를 보낸다. 이는 내부 DNS 서버(e.g., K8s의 CoreDNS)에 부하를 집중시켜 네임서버 자체의 응답 지연을 유발한다.

### 2) JVM DNS 캐싱의 함정
자바 기반 백엔드(Spring Boot 등) 환경에서는 언어 런타임 차원의 추가적인 문제가 발생한다. JVM은 보안 및 성능상의 이유로 한 번 조회한 DNS 응답을 자체 메모리에 별도로 캐싱한다.
* 과거 JVM의 기본 보안 정책(`java.security`)에서 `networkaddress.cache.ttl`의 기본값은 보안 관리자가 설정되어 있을 경우 **무한(-1)**으로 설정되어 있었다.
* 보안 관리자가 없더라도 기본값이 수십 초 이상으로 고정되는 경우가 많다. 따라서 상위 DNS 서버가 레코드를 갱신하더라도 실행 중인 애플리케이션은 이를 즉시 인지하지 못하고 과거 IP로 요청을 계속 보낸다.

### 3) 내부 통신(East-West)에서의 L4/L7 한계
전통적인 L4/L7 로드밸런서(F5, NetScaler, AWS ALB/NLB)를 서비스 간 호출마다 배치하는 방식 역시 한계가 명확하다.

| 비교 항목 | 외부 유입 트래픽 (North-South) | 서비스 간 내부 통신 (East-West) |
| :--- | :--- | :--- |
| **트래픽 비중** | 전체 트래픽의 약 10\~20% | 전체 트래픽의 약 **80\~90%** |
| **L4/L7 적용 시 문제** | 최전방 단일 진입점으로 적합함 | 모든 홉마다 프록시를 거치며 **네트워크 레이턴시 누적(+1 Hop)** |
| **비용 및 리소스** | 게이트웨이 장비 몇 대로 통제 가능 | 서비스 수 증가에 따라 장비 증설 비용 및 처리량 병목 급증 |
| **단일 장애점 (SPOF)** | 고가용성(HA) 구성으로 방어 | 중앙 로드밸런서 장애 시 사내 모든 마이크로서비스 간 통신 완전 마비 |

외부에서 유입되는 트래픽은 하드웨어 로드밸런서로 안전하게 제어할 수 있지만, 수백 개의 마이크로서비스가 초당 수만 번씩 주고받는 내부 통신을 중앙 로드밸런서로 통과시키는 것은 비용, 지연 시간, 장애 격리 측면에서 지속 불가능하다.

## 3. 서비스 디스커버리 핵심 개념

서비스 디스커버리는 애플리케이션 수준에서 실시간으로 갱신되는 동적 인메모리 주소 저장소를 기반으로 작동한다.

앞서 살펴본 DNS의 캐싱 한계와 L4/L7의 병목을 극복하기 위해 등장한 패러다임이 바로 **서비스 디스커버리(Service Discovery)**다. 서비스 디스커버리는 복잡한 하드웨어 스위치나 정적 설정 없이, 소프트웨어 수준에서 인스턴스의 위치를 실시간으로 등록하고 추적하는 주소 관리 역할을 수행한다.

```mermaid
flowchart TD
    subgraph Roles ["서비스 디스커버리의 3대 구성요소"]
        Reg["1. Service Registry (주소 저장소)<br/>- 서비스명 기반 엔드포인트 목록 인메모리 관리<br/>- 헬스체크 및 만료 노드 제거"]
        Provider["2. Service Provider (피호출자)<br/>- 부팅 시 자신의 IP:Port 등록<br/>- 주기적 하트비트 전송"]
        Consumer["3. Service Consumer (호출자)<br/>- 레지스트리에 Provider 주소 목록 질의<br/>- 획득한 IP로 직접 비즈니스 요청 수행"]
    end

    Provider -->|"① 등록 (Register)"| Reg
    Provider -.->|"② 생존 신고 (Heartbeat)"| Reg
    Consumer -->|"③ 위치 조회 (Lookup)"| Reg
    Consumer ==>|"④ 직접 통신 (Direct RPC)"| Provider
```

### 1) 서비스 레지스트리 (Service Registry)
서비스 디스커버리의 중심 구성요소는 **서비스 레지스트리(Service Registry)**라는 고가용성 데이터베이스다. 레지스트리는 단순한 Key-Value 구조를 유지한다.

```text
Key: "order-service"
Value: [
  { "ip": "10.244.1.20", "port": 8080, "weight": 100, "healthy": true, "zone": "ap-northeast-2a" },
  { "ip": "10.244.2.45", "port": 8080, "weight": 100, "healthy": true, "zone": "ap-northeast-2b" },
  { "ip": "10.244.3.12", "port": 8080, "weight": 50,  "healthy": false, "zone": "ap-northeast-2c" }
]
```
* **서비스 논리명(Service Name)**을 식별자로 사용한다.
* 해당 서비스 논리명 아래 현재 정상적으로 살아 있는 **물리 인스턴스들의 배열(IP, Port, 가중치, 가용영역 메타데이터 등)**을 매핑한다.

### 2) 제어 평면(Control Plane)과 데이터 평면(Data Plane)의 분리
서비스 디스커버리 아키텍처가 높은 처리 성능을 내는 이유는 **위치 정보를 묻는 제어 통신(Control Plane)**과 **비즈니스 페이로드를 전송하는 데이터 통신(Data Plane)**을 분리했기 때문이다.
* **제어 평면**: Consumer는 Provider의 위치가 필요할 때 레지스트리에 접속해 IP 목록만 받아온다(Look-up).
* **데이터 평면**: 실제 주문, 결제 등의 대용량 HTTP/gRPC 트래픽은 레지스트리를 거치지 않고, Consumer가 Provider의 IP로 **직접 점대점(Peer-to-Peer, 1-Hop) 통신**을 수행한다.
* 따라서 레지스트리 서버에 병목이 생기지 않으며, 레지스트리가 잠시 일시적 장애를 겪더라도 클라이언트는 이미 조회한 로컬 주소 정보로 정상 통신을 유지할 수 있다.

## 4. 탐색 주체별 두 가지 패턴

서비스 디스커버리를 구현하는 방식은 주소 탐색과 부하 분산의 책임을 '호출하는 쪽'에 두느냐, '중간 인프라'에 두느냐에 따라 나뉜다.

위치 해석의 주체와 로드밸런싱 위치에 따라 크게 **클라이언트 사이드 디스커버리(Client-Side Discovery)**와 **서버 사이드 디스커버리(Server-Side Discovery)** 두 가지 방식으로 구분한다.

```mermaid
flowchart TB
    subgraph ClientSide ["클라이언트 사이드 디스커버리 (예: Eureka, Nacos)"]
        direction TB
        C_Client["Client (Consumer)<br/>+ 로컬 캐시 & 로드밸런서 내장"]
        C_Reg["Service Registry"]
        C_P1["Provider Instance A"]
        C_P2["Provider Instance B"]

        C_Client -.->|"① IP 목록 조회 & 캐싱"| C_Reg
        C_Client ==>|"② 1-Hop 직접 호출 (Direct)"| C_P1
    end

    subgraph ServerSide ["서버 사이드 디스커버리 (예: K8s Service, AWS ALB)"]
        direction TB
        S_Client["Client (Consumer)<br/>(단순 HTTP 요청)"]
        S_Proxy["Router / Load Balancer<br/>(Kube-Proxy, ALB)"]
        S_Reg["Service Registry<br/>(K8s Endpoints)"]
        S_P1["Provider Instance A"]
        S_P2["Provider Instance B"]

        S_Proxy -.->|"① 대상 인스턴스 추적"| S_Reg
        S_Client -->|"② 고정 VIP/DNS 호출"| S_Proxy
        S_Proxy ==>|"③ 2-Hop 포워딩"| S_P2
    end
```

### 1) 클라이언트 사이드 디스커버리 (Client-Side Discovery)
Netflix Eureka, Alibaba Nacos, Spring Cloud LoadBalancer(과거 Ribbon) 등이 채택한 대표적인 방식이다.

* **동작 방식**: 
  1. 클라이언트(Consumer)는 애플리케이션 시작 시 레지스트리 서버로부터 타깃 서비스의 인스턴스 전체 목록을 가져와 로컬 메모리에 캐싱한다.
  2. 이후 비즈니스 요청이 발생하면, 클라이언트 내부에 내장된 로드밸런서 알고리즘(Round-Robin, Weighted, Least Connections 등)이 캐시 목록 중 적절한 인스턴스를 하나 선택한다.
  3. 클라이언트는 선택된 IP:Port로 중간 매개체 없이 직접 통신(1-Hop)한다.
* **장점**:
  * **짧은 지연 시간(Low Latency)**: 중간 프록시를 거치지 않고 직접 통신하므로 네트워크 홉이 추가되지 않는다.
  * **세밀한 라우팅**: 클라이언트 코드 수준에서 가용영역(Zone Aware), 카나리 배포(Canary), 사용자 헤더 기반의 트래픽 분기가 가능하다.
* **단점**:
  * **두꺼운 언어 종속적 SDK**: 클라이언트가 레지스트리 통신 규약과 로드밸런싱 알고리즘을 코드로 포함해야 한다. Java/Spring Cloud 환경에서는 편리하지만, Node.js, Go, Python 등 다양한 언어가 혼재된 폴리글랏(Polyglot) 환경에서는 각 언어별 라이브러리를 모두 개발하고 관리해야 하는 운영 부담이 발생한다.

### 2) 서버 사이드 디스커버리 (Server-Side Discovery)
Kubernetes의 Service(kube-proxy 및 CoreDNS)와 AWS ALB/NLB가 대표적으로 채택하는 방식이다.

* **동작 방식**:
  1. 클라이언트는 개별 인스턴스의 동적 IP를 알 필요가 없다. 대신 안정적인 고정 가상 IP(VIP)나 DNS 이름(e.g., `http://payment-service.default.svc.cluster.local`)으로 요청을 보낸다.
  2. 네트워크 경로 중간에 위치한 로드밸런서(또는 커널 레벨의 iptables/IPVS)가 레지스트리(K8s Endpoints)를 참조하여 트래픽을 실제 살아 있는 컨테이너 중 하나로 포워딩(2-Hop)한다.
* **장점**:
  * **언어 중립성(Polyglot Agnostic)**: 클라이언트 애플리케이션은 디스커버리 로직이 전혀 필요 없다. 표준 HTTP/REST 클라이언트만 있으면 어떤 프로그래밍 언어로 작성되었든 동일하게 호출할 수 있다.
* **단점**:
  * **프록시 오버헤드**: 중간에 로드밸런서 계층을 거치므로 추가적인 네트워크 레이턴시가 발생하며, 로드밸런서 인프라의 가용성과 용량 한계를 지속적으로 관리해야 한다.

### 3) 전파 지연과 클라이언트 자체 결함 격리

"서비스 레지스트리가 존재하면 클라이언트의 서비스 호출 실패는 모두 방지되는가?"

현실의 분산 시스템에서는 그렇지 않다. 서비스 디스커버리는 구조적으로 상태 동기화가 늦어지는 **전파 지연(Propagation Lag)**을 피할 수 없다. 이 공백 동안 호출 측으로 장애가 퍼져 **연쇄 장애(Cascading Failure)**가 일어나지 않도록, 클라이언트는 **재시도(Retry)**와 **서킷 브레이커(Circuit Breaker)**로 자체 결함을 격리해야 한다.

#### 1. 전파 지연과 연쇄 장애 시나리오
결제 서비스 인스턴스 3대(`A: 10.0.0.1`, `B: 10.0.0.2`, `C: 10.0.0.3`)가 동작 중일 때, 주문 서비스의 로컬 캐시에는 세 주소가 모두 등록되어 있다고 가정하자.
* **10:00:00 (인스턴스 비정상 종료)**: 결제 서버 `A`가 메모리 누수(OOM)로 예기치 않게 종료된다.
* **10:00:00 \~ 10:00:30 (레지스트리 감지 지연)**: 레지스트리는 하트비트 타임아웃(통상 30초)이 경과하기 전까지 `A`의 종료를 감지하지 못하고 만료 처리를 미룬다.
* **10:00:00 \~ 10:01:00 (클라이언트 캐시 불일치)**: 주문 서비스가 주기적 폴링(30초 간격)으로 목록을 갱신한다면, 최악의 경우 레지스트리 만료 직전에 폴링을 마친 상태가 겹쳐 **최대 60초(30초 + 30초)** 동안 이전 목록을 유지할 수 있다.

이 최대 60초의 공백 동안 주문 서비스로 초당 100건의 트래픽이 유입되면, 라운드로빈에 의해 초당 약 33건의 요청이 이미 종료된 `A`로 계속 전송된다. 클라이언트는 TCP 연결 타임아웃(예: 3초) 동안 응답을 기다리며 블로킹되고, 수 초 만에 **주문 서비스의 요청 처리 스레드 풀(예: 200개)이 고갈(Thread Starvation)**된다. 결국 결제 서버 한 대의 장애가 주문 서비스 전체를 마비시키는 연쇄 장애로 번진다.

#### 2. 클라이언트의 2단계 결함 격리 메커니즘
중앙 레지스트리 동기화가 끝나기 전까지 클라이언트는 로컬 계층에서 두 단계 방어를 실행한다.
* **1단계, 페일오버 재시도(Failover Retry)**: `A(10.0.0.1)` 호출이 연결 거부(`ConnectException`)되면 바로 에러를 내지 않는다. 대신 로컬 캐시의 정상 인스턴스 `B(10.0.0.2)`로 즉시 우회해 재호출함으로써 요청을 완료한다.
* **2단계, 서킷 브레이커(Circuit Breaker)**: 매 요청마다 `A`에 연결을 시도하다 실패한 뒤 `B`로 넘어가면 지연 시간과 스레드 소모가 남는다. 이때 최근 실패율이 임계치를 넘기면 클라이언트 내 서킷 브레이커가 회로를 **OPEN(차단)**으로 전환한다. 이후 `A`로 향하는 트래픽은 네트워크 시도 없이 0ms 만에 즉시 차단(Fail-Fast)되어 스레드 블로킹을 막는다.

| 구분 | 중앙 서비스 레지스트리 | 클라이언트 복원력 (재시도 및 서킷 브레이커) |
| :--- | :--- | :--- |
| **처리 수준** | 레지스트리 계층의 엔드포인트 말소 | 호출자 계층의 즉각적 결함 격리(Fail-Fast) |
| **반영 속도** | 수십 초 단위 (주기적 동기화 지연) | 즉각적 (임계치 도달 후 0ms 차단) |
| **핵심 역할** | 전체 시스템의 장기적 위치 동기화 | 레지스트리 갱신 공백 동안 호출 측 스레드 고갈 방지 |

서비스 디스커버리는 전파 지연을 피할 수 없으므로, **레지스트리가 전체 위치를 동기화하는 동안 클라이언트가 재시도와 서킷 브레이커로 즉시 연쇄 장애를 끊는 상호 보완 구조**가 필요하다.

## 5. 레지스트리 내부 생명주기

인스턴스의 등록부터 생존 검증, 그리고 안전한 퇴출에 이르기까지 레지스트리는 엄격한 상태 전이 규칙을 따른다.

서비스 레지스트리가 수천 개의 동적 인스턴스 위치를 오차 없이 추적하기 위해서는 정교한 생명주기(Lifecycle) 관리 프로토콜이 필수적이다.

```mermaid
stateDiagram-v2
    [*] --> Starting: 인스턴스 부팅
    Starting --> Registered: 자가 등록 / 3rd Party 등록
    
    state Registered {
        [*] --> Healthy: 초기 헬스체크 통과
        Healthy --> Healthy: 주기적 하트비트 수신 (Push)<br/>또는 서버 헬스체크 프로브 (Pull)
        Healthy --> Unhealthy: 하트비트 누락 (임계치 초과)
        Unhealthy --> Evicted: 만료 시간 초과 (Registry Eviction)
    }

    Registered --> Deregistered: 정상 셧다운 훅 (Graceful Shutdown)
    Deregistered --> [*]
    Evicted --> [*]
```

### 1) 등록(Registration): 자가 등록 vs 제3자 등록
* **자가 등록(Self-Registration)**: 인스턴스 프로세스가 직접 자신의 IP, 포트, 메타데이터를 파악하여 기동 시점에 레지스트리 REST/gRPC API를 호출해 자신을 등록한다(Spring Cloud Eureka/Nacos Client 방식). 구현이 직관적이지만 애플리케이션이 등록 라이브러리를 포함해야 한다.
* **제3자 등록(3rd Party Registration)**: 인스턴스 자체는 아무것도 하지 않는다. 외부의 독립된 오케스트레이터 에이전트(예: Kubernetes Kubelet, Docker Registrator)가 컨테이너의 생성과 종료 이벤트를 감지하여 레지스트리에 대신 등록하고 삭제한다.

### 2) 생존 검증(Health Check): Push vs Pull
등록된 인스턴스가 여전히 정상 동작 중인지 판별하는 방식도 두 갈래로 나뉜다.
* **클라이언트 푸시(Heartbeat)**: 인스턴스가 5초, 10초 주기로 레지스트리에 경량 생존 확인 패킷을 보낸다(Eureka, Nacos 임시 인스턴스). 네트워크 부하가 분산되는 장점이 있다. 반면 프로세스는 살아 있으나 스레드풀 고갈이나 DB 연결 단절로 요청을 못 처리하는 상태는 늦게 감지할 수 있다.
* **서버 풀(Probe)**: 레지스트리가 각 인스턴스의 헬스체크 경로로 HTTP/TCP 프로브 요청을 직접 전송한다(Consul, Kubernetes Probe). 실제 처리 가능 여부를 더 깊이 확인하지만, 인스턴스 수가 늘수록 레지스트리의 아웃바운드 점검 부하가 증가한다.

### 3) 우아한 퇴출(Graceful Shutdown)과 비정상 축출(Eviction)
* **정상 종료(Graceful Deregistration)**: 애플리케이션이 `SIGTERM` 신호를 수신하면 종료 훅(Shutdown Hook)을 가동하여 레지스트리에 등록 해제(`deregister`) 요청을 보낸다. 레지스트리는 해당 인스턴스를 즉시 목록에서 제거하고 클라이언트들에게 알린다.
* **비정상 축출(Eviction)**: 노드 전원이 꺼지거나 네트워크 단절로 하트비트가 일정 시간(e.g., 30초) 동안 도달하지 않으면, 레지스트리의 백그라운드 퇴출 타이머가 작동하여 해당 인스턴스를 강제로 레지스트리에서 말소한다.

---

> [!NOTE]
> **CAP 정리와 서비스 레지스트리 (AP vs CP의 선택)**
>
> 분산 시스템의 **CAP 정리**는 네트워크 단절(Partition tolerance, P) 상황에서 모든 노드가 같은 데이터를 보는 **일관성(Consistency, C)**과 요청에 항상 응답하는 **가용성(Availability, A)** 중 하나를 우선해야 한다는 원칙이다.
>
> 과거에는 데이터 일관성(C)을 우선하는 **CP 시스템**(ZooKeeper 등 **정족수(Quorum, 과반수 합의)** 기반 레지스트리)을 많이 썼다. 그러나 네트워크 단절이 발생해 과반수 노드가 모이지 않으면 레지스트리가 쓰기와 조회를 전면 중단했다. 결과적으로 레지스트리 장애 때문에 신규 배포와 오토스케일링까지 멈추는 문제가 생겼다.
>
> 현대 서비스 디스커버리(Eureka, Nacos 임시 인스턴스)는 **AP(가용성 우선)**를 지향한다.
> * 동기화 지연 때문에 이미 종료된 주소가 2\~3초 더 남아 있더라도, 레지스트리는 멈추지 않고 가용한 주소 목록을 즉시 반환한다.
> * 잘못 전달된 주소로 생기는 일시적 호출 오류는 클라이언트의 서킷 브레이커와 재시도 로직으로 우회한다.
>
> Nacos의 경우 상태가 없는 서비스 인스턴스 목록은 고성능 비동기 전파(AP 지향 **Distro** 프로토콜)로 다루고, 강한 일관성이 필요한 설정 정보는 과반수 합의 기반(**Raft** CP 프로토콜)으로 분리해 처리한다.

## 6. K8s와 디스커버리의 미래

Kubernetes가 인프라 표준이 된 현재, 서비스 디스커버리는 사이드카 기반의 서비스 메시(Service Mesh)로 진화하며 장점만을 흡수하고 있다.

현대 인프라에서 널리 쓰이는 Kubernetes는 자체 서비스 디스커버리 구성요소(CoreDNS, K8s Service, kube-proxy)를 기본 내장하고 있다. 그렇다면 대규모 분산 환경에서는 왜 여전히 Nacos나 Eureka 같은 애플리케이션 레벨 레지스트리를 병행하거나, Istio 같은 서비스 메시로 넘어가는 것일까?

### 1) K8s Service 환경에서 Eureka/Nacos가 공존하는 이유
쿠버네티스의 내장 Service(kube-proxy)는 L4 수준(IP와 포트 기반)의 패킷 포워딩에 기초한다. 반면 고도화된 서비스 환경에서는 다음과 같은 애플리케이션 레벨 제어가 필요하다.
1. **멀티 클러스터 및 하이브리드 클라우드 통신**: K8s 클러스터 내부의 파드와 기존 온프레미스 레거시 VM 서버 간에 동일한 서비스 논리명으로 통신해야 하는 경우, 단일 K8s 클러스터 범위를 넘어서는 통합 레지스트리가 필요하다.
2. **풍부한 메타데이터 기반 라우팅**: HTTP 헤더, 사용자 등급, 버전 메타데이터(`version=v2.1`)에 기반하여 특정 트래픽만 카나리 인스턴스로 보내는 세밀한 제어는 순수 K8s Service만으로 구현하기 까다롭다.
3. **애플리케이션 계층 프레임워크 연동**: 선언적 HTTP 클라이언트나 서킷 브레이커 라이브러리 등 기존 애플리케이션 코드를 쿠버네티스 API에 직접 묶지 않고 유지할 수 있다.

### 2) 서비스 메시(Service Mesh) 구조로의 발전
클라이언트 사이드와 서버 사이드 디스커버리 간의 트레이드오프는 **서비스 메시(Service Mesh, e.g. Istio + Envoy)** 아키텍처를 통해 보완되고 있다.

```mermaid
flowchart LR
    subgraph Pod1 ["Consumer Pod"]
        App1["Consumer App<br/>(단순 HTTP 요청)"]
        Envoy1["Envoy Proxy (Sidecar)<br/>(클라이언트 로드밸런서 내장)"]
        App1 -->|"localhost 호출"| Envoy1
    end

    subgraph ControlPlane ["Istio Control Plane (istiod)"]
        MeshReg["Service Registry<br/>(K8s Services / Endpoints 추적)"]
    end

    subgraph Pod2 ["Provider Pod"]
        Envoy2["Envoy Proxy (Sidecar)"]
        App2["Provider App"]
        Envoy2 -->|"localhost 전달"| App2
    end

    MeshReg -.->|"엔드포인트 동적 푸시 (xDS API)"| Envoy1
    Envoy1 ==>|"1-Hop 직접 mTLS 통신"| Envoy2
```

서비스 메시는 **"양쪽 패턴의 장점을 취합"**하는 방식을 채택했다.
* **언어 독립성 확보 (서버 사이드의 장점)**: 애플리케이션 프로세스는 더 이상 SDK나 디스커버리 코드를 직접 포함하지 않는다. 로컬호스트(`localhost:8080`)의 사이드카 프록시(Envoy)로 HTTP 호출을 보낼 뿐이다.
* **1-Hop 직접 통신 및 세밀한 라우팅 (클라이언트 사이드의 장점)**: 각 파드마다 붙어 있는 Envoy 사이드카 프록시가 컨트롤 플레인(istiod)으로부터 실시간 서비스 레지스트리 정보를 동기화받는다. 그리고 Envoy가 직접 목적지 파드의 Envoy로 **중간 중앙 로드밸런서 없이 1-Hop 직접 통신**을 수행한다.
* 또한 이 과정에서 서비스 간 상호 TLS(mTLS) 암호화와 트래픽 관찰성(Metrics, Distributed Tracing)까지 인프라 차원에서 처리된다.

## 7. 디스커버리 패턴 비교와 요약

모놀리스에서 분산 클라우드 전환 과정에서 서비스 디스커버리는 필수 통신 인프라다.

| 진화 단계 | 주소 해결 주체 | 로드밸런싱 위치 | 장점 | 단점 / 극복 과제 |
| :--- | :--- | :--- | :--- | :--- |
| **모놀리스** | OS / 컴파일러 | 필요 없음 (단일 메모리) | 레이턴시 0ms, 단순함 | 수평 확장 한계, 단일 장애점 |
| **전통 DNS / L4** | DNS 서버, 중앙 L4/L7 | 중앙 하드웨어 스위치 | 표준 규격, 단순함 | TTL 딜레마, 2-Hop 지연, East-West 병목 |
| **클라이언트 사이드**<br/>(Eureka, Nacos) | 클라이언트 SDK | 클라이언트 애플리케이션 | 1-Hop 직접 통신, 세밀한 라우팅 | 언어 종속 SDK 부담, 클라이언트 복잡도 |
| **서버 사이드**<br/>(K8s Service) | K8s CoreDNS / iptables | 커널 프록시 (kube-proxy) | 언어 중립성 | 프록시 홉 오버헤드, 세밀한 L7 제어 한계 |
| **서비스 메시**<br/>(Istio / Envoy) | 컨트롤 플레인 (istiod) | 로컬 사이드카 (Envoy) | 언어 중립성 + 1-Hop 통신 + 보안 | 사이드카 컨테이너 자원 소비(CPU/Mem) |

서비스 디스커버리는 동적으로 생성되고 종료되는 분산 노드의 주소를 빠르고 안정적으로 추적하기 위한 통신 인프라다.

* **제어와 데이터 경로 분리**: 레지스트리는 위치 조회만 맡고 실제 호출은 클라이언트와 서버가 직접 주고받아 중앙 병목을 없앤다.
* **전파 지연 보완**: 레지스트리 동기화 공백 동안에는 클라이언트 측 재시도와 서킷 브레이커로 스레드 고갈과 연쇄 장애를 차단한다.
* **운영 환경에 맞는 선택**: 언어 다양성, 프록시 홉 허용치, 라우팅 제어 수준, CAP 정리상의 가용성 우선 여부에 따라 클라이언트 사이드, 서버 사이드, 서비스 메시 중 알맞은 패턴을 고른다.
